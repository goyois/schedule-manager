# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, and any other AGENTS.md-aware tool) when
working with code in this repository. `CLAUDE.md` is a symlink to this file, kept for tools that only
look for that specific filename.

## Commands

```bash
./gradlew bootRun                                    # run the app (default profile: local)
./gradlew build                                      # compile + test + package
./gradlew compileJava compileTestJava -q              # fast compile check without running tests
./gradlew test                                       # run all tests
./gradlew test --tests "ScheduleServiceTest"          # run a single test class
./gradlew test --tests "ScheduleServiceTest.apiPerformance"  # run a single test method
```

Local infra required to run the app: PostgreSQL 16+ (db `api`) and Redis 7.x, both on default ports. `src/main/resources/application-local.yml` (gitignored) holds datasource creds, Redis host, the Anthropic API key, the JWT secret, and the Google OAuth client ID (`google.oauth.client-id`) — it must exist locally and is not checked in. `src/main/resources/application.yml` only has profile-independent settings (Redis timeout, actuator exposure).

> Migrated from MySQL to PostgreSQL — see `TASK.md` for the migration record and the MySQL vs PostgreSQL rationale (driven by future Spring AI + RAG/pgvector work).

**⚠️ `spring.jpa.hibernate.ddl-auto` is `validate`, not `update`, in `application-local.yml`.** Hibernate will *not* auto-create new columns/tables — adding or changing an entity field requires a matching manual `ALTER TABLE`/`CREATE TABLE` against the local `api` database (e.g. `psql -h localhost -U <user> -d api -c "ALTER TABLE ... ADD COLUMN ..."`) before the app boots or `@SpringBootTest` tests run, or you'll get `SchemaManagementException: Schema-validation: missing column [...]` at context startup. String-backed enum columns (e.g. `ai_chat_messages.role`) additionally get a `CHECK (col IN (...))` constraint by convention — match it for new enum columns. See the collation-migration DDL further down for the same pattern.

Monitoring stack (optional, not required for app to run): `docker-compose -f monitoring/docker-compose.yml up` starts Prometheus (`:9090`) and Grafana (`:3000`, admin/admin). The app exposes `/actuator/prometheus` unauthenticated (permitted in `SecurityConfig`) for scraping.

Production deployment (AWS EC2 + RDS/ElastiCache + ECR, GitHub Actions-driven build/test/deploy pipeline via OIDC — no long-lived AWS keys stored in GitHub): see `DEPLOYMENT.md`. `Dockerfile`/`.github/workflows/deploy.yml`/`deploy/` and `application-prod.yml` back that pipeline — `application-prod.yml` is checked in (unlike `application-local.yml`) since every value is an env-var placeholder, no real secrets.

## Architecture

Spring Boot 3.4 / Java 17, package-by-domain under `com.example.schedule_manager`:

- `domain/{user,auth,schedule,category,recurringschedule,ai,mandalart}` — each has `controller/`, `service/`, `repository/`, `entity/`, and (except auth) `dto/`. DTOs are Java records; entities use Lombok `@Builder` with a private all-args constructor and protected no-args constructor, and expose mutation only through explicit `update(...)` methods (no public setters).
- `global/security/` — JWT auth stack, split into subpackages: `config/SecurityConfig` (stateless, CSRF disabled, permits `/api/auth/**`, `POST /api/users`, static view routes, `/actuator/**`), `filter/JwtAuthenticationFilter` (runs before `UsernamePasswordAuthenticationFilter`, resolves `Bearer` token — or a query param for the SSE stream route — checks a Redis logout blacklist, populates `SecurityContext`), `util/JwtUtil` (HS-signed JWT, email as subject, issues both access and refresh tokens), `service/CustomUserDetailsService` (loads `User` by email, grants `ROLE_USER`/`ROLE_ADMIN` from `UserType`).
- `global/config/GoogleOAuthConfig` — provides a `GoogleIdTokenVerifier` bean (audience = `google.oauth.client-id`) used by `AuthService.loginWithGoogle`. Google login is credential-flow, not Spring Security's `oauth2Login()`: the frontend obtains a Google ID token via Google Identity Services (GIS) client-side JS, POSTs it to `POST /api/auth/google`, the server verifies the token's signature/audience/expiry against Google's public keys, then get-or-creates a `User` by email (`AuthProvider.GOOGLE` for new accounts, `password` set to an unusable random BCrypt hash since `CustomUserDetailsService`/`UserDetails` require a non-null password) and issues the same app JWT as password login. No redirect/authorization-code flow, no Google client secret needed.
- `global/config/RedisConfig` + `CacheFailSafeErrorHandler` — Redis-backed `CacheManager` for `@Cacheable`/`@CacheEvict`. Custom `GenericJackson2JsonRedisSerializer` registers `JavaTimeModule` (required for caching DTOs with `LocalDateTime` fields). `CacheFailSafeErrorHandler` makes cache get/put/evict failures fail-open (log + fall through to DB) instead of turning a Redis outage into a 500 — the same fail-open pattern is used in `JwtAuthenticationFilter`'s blacklist check.
- `global/config/AiConfig` — provides the `ChatClient` bean used by `AiService`.
- `global/exception/` — `GlobalExceptionHandler` (`@RestControllerAdvice`) maps `BusinessException` (carries an `ErrorCode` with its own `HttpStatus` + message), `MethodArgumentNotValidException`, `AuthenticationException`, `AccessDeniedException`, and any other `Exception` to `ApiResponse.error(...)` with the right status. Services throw `BusinessException(ErrorCode.XXX)` for not-found/validation/authorization/conflict failures (e.g. `ScheduleService` ownership checks) instead of raw `IllegalArgumentException` — see `ErrorCode` for the full catalog.
- `global/response/ApiResponse<T>` — every controller returns `ResponseEntity<ApiResponse<T>>` via `ApiResponse.success(data)` / `.success()` / `.error(code, message)`.
- `global/common/BaseEntity` — `@MappedSuperclass` with `@CreatedDate`/`@LastModifiedDate` (JPA auditing).
- `global/controller/ViewController` — forwards clean paths (`/`, `/login`, `/signup`, `/dashboard`, `/mandalart`, `/settings`) to static HTML in `src/main/resources/static/` (vanilla JS frontend: `dashboard.js`, `login.js`, `signup.js`, `mandalart.js`, `api.js`, ...).

**Authorization model**: `UserType` is `ADMIN` or `USER`. In `ScheduleService`, `ADMIN` can pass an arbitrary `userId` to read/target any user's schedules; `USER` always has the requester's own id substituted in, ignoring any `userId` param from the request. Ownership on single-resource reads (`getSchedule`) is enforced by comparing `schedule.getUser().getId()` to the authenticated requester.

**Category ownership model**: `Category.user` is nullable and has three meanings, all handled uniformly by `CategoryService.isVisibleTo`/`isAdminOwned`: `null` = legacy category predating this ownership column (visible to everyone, freely editable/deletable by anyone who can see it); owner has `UserType.ADMIN` = a "기본 설정 카테고리" (default category), visible to every user but not editable/deletable by a `USER` requester (`ErrorCode.DEFAULT_CATEGORY_UPDATE_FORBIDDEN`/`DEFAULT_CATEGORY_DELETE_FORBIDDEN`) — an `ADMIN` requester *can* delete their own default categories (`deleteCategory` only blocks this for non-`ADMIN` requesters); owner is a `USER` = private to that user, and invisible to everyone else (`getCategory`/`updateCategory`/`deleteCategory` all collapse "exists but not visible" into `CATEGORY_NOT_FOUND` rather than leaking existence via a 403). Deletion is additionally blocked for any category (default or personal) still referenced by a schedule (`scheduleRepository.existsByCategoryId`), regardless of requester role, since the FK constraint would otherwise surface as a raw DB exception.

**Auth tokens**: `AuthService` issues an access token and a refresh token together on login (`/api/auth/login`, `/api/auth/google`). The refresh token is stored in Redis as `refresh:{email}` (TTL = its own remaining expiration), single-session-per-user (re-login overwrites and implicitly revokes the previous one). `POST /api/auth/refresh` validates the presented refresh token against the stored one and rotates both tokens. `POST /api/auth/logout` blacklists the access token (`blacklist:{token}`, TTL = remaining expiration) and deletes the stored refresh token.

**Caching**: `ScheduleService.getSchedules` is cached under cache name `schedules` with key `requesterEmail-userId-categoryId` (empty results are not cached). Mutating methods (`create`/`update`/`deleteSchedule`) no longer do a full-cache `allEntries = true` evict — they `SCAN` (not blocking `KEYS`) for `schedules::*-{userId}-*` plus `schedules::*-null-*` (to also catch ADMIN's un-scoped `userId=null` list-all entries) and delete just those keys, failing open on Redis errors. See [[project_schedule_cache_evict_scan]] and [[project_schedule_cache_versioning_followup]] for the history/next-step here. Every cache eviction also calls `ScheduleEventPublisher.notifyChanged(userId)` to push the change over SSE.

**Real-time updates**: `GET /api/schedules/stream` (SSE, `SseEmitter`) lets the dashboard react to schedule changes without polling. Because `EventSource` can't send custom headers, `JwtAuthenticationFilter` accepts the JWT via a query param on this route specifically. `ScheduleEventPublisher` fires on every schedule mutation (see Caching above) and on automatic status transitions.

**Board pagination**: `GET /api/schedules/board?status=&page=&size=&categoryId=` is a separate, uncached endpoint used only by the dashboard's board view "더보기" — `ScheduleService.getBoardSchedules` / `ScheduleRepositoryImpl.searchBoardSchedules` (QueryDSL, real `LIMIT`/`OFFSET` + a `PageableExecutionUtils` count query) page through a single status column scoped to "today" (`LocalDate.now()` midnight to midnight+1, mirroring `dashboard.js`'s `schedulesOverlappingRange`). `GET /api/schedules` (the full, unpaginated list) is deliberately left untouched and still backs the calendar/radar/clock/achievement widgets, which need a whole date range at once — see README.md's "아직 미구현" note on this split. `dashboard.js`'s `boardColumnVisibleCount` map now drives the `size` query param (offset always 0, size grows by `BOARD_COLUMN_VISIBLE_LIMIT` per "더보기" click) instead of slicing an already-fetched array.

**AI integration**: `domain/ai` is implemented and does call the real Anthropic API via `ChatClient` (`AiConfig`). `AiService.sendMessage` builds a system prompt with categories + a schedule context window (last 2 weeks / next 2 weeks, to bound token cost) plus up to the last 20 turns of chat history (persisted in `AiChatMessage`/Postgres), and returns a structured suggestion (`AiScheduleSuggestion`) the frontend can register as a real schedule via `PATCH /api/ai/chat/messages/{id}/register`. `User.aiAutoRegisterEnabled` (toggle via `PUT /api/users/me/ai-auto-register`) controls whether suggestions are registered automatically instead of requiring manual confirmation. Design history/rationale: `AI_STRATEGY.md`. Calling this endpoint spends real Anthropic API credits — be deliberate about when to actually invoke it (curl/manual testing/live e2e tests) versus relying on the mocked `AiServiceTest`.

**AI response classification**: every `AiScheduleSuggestion` the model returns is classified into `AiResponseCategory.SCHEDULE_RECOMMENDATION` (new schedule), `.SCHEDULE_UPDATE` (edit an existing one), `.MANDALART_FILL` (fill a mandalart board's empty cells — see the Mandalart section below), or `.GENERAL` (a required field in the structured-output schema, driven by `AiService.SYSTEM_PROMPT` — the prompt spells out this exact priority order and is deliberately assertive about it, since the model would otherwise default to re-recommending an existing schedule instead of classifying "move/change/reschedule X" requests as an update). Only `SCHEDULE_RECOMMENDATION`/`SCHEDULE_UPDATE` responses get `title`/`startAt`/`endAt`/`categoryId` populated and persisted — for `GENERAL`/`MANDALART_FILL` (or a null/unrecognized category, treated as `GENERAL` defensively), `AiService.sendMessage` force-nulls all schedule-suggestion fields itself regardless of what the model actually filled in, so a prompt-following slip on the model's side can't leak a stray registration/edit option into the UI. `category` is persisted on `AiChatMessage`/exposed on `AiChatMessageDto` (as its enum name string), and `dashboard.js`'s `aiChatAssistantBubbleHtml` branches on `message.category` (not field-presence sniffing) to decide whether/which action buttons to render. `ai_chat_messages.category` is a nullable `varchar(255)` with a `CHECK` constraint restricting it to the four enum values (added via manual DDL — see the `ddl-auto: validate` note above).

**AI multi-schedule recommendation** (`SCHEDULE_RECOMMENDATION`): a single turn can suggest several new schedules at once (e.g. "이번 주에 운동, 팀 회의, 병원 예약 등록해줘") instead of just one. `AiScheduleSuggestion.scheduleItems` is a list the model fills one element per requested schedule (always populated, even for a single suggestion — the top-level `title`/`content`/`startAt`/`endAt`/`categoryId` fields are `SCHEDULE_UPDATE`-only now and stay null for recommendations). `AiService.sendMessage` sanitizes each element independently (`categoryId` validated against `[사용 가능한 카테고리]`, `endAt` bumped a day if it doesn't fall after `startAt` — for same-day timestamps where the model represented a midnight-crossing event without incrementing the date) — the original single-suggestion path used to also force every date to today regardless of what the model said, but that broke the moment multi-item requests started asking for schedules on specific (often future) days, e.g. "다음 주 월/화/수/금/토/일 3분할 루틴 등록해줘" landing everything on today instead; `sanitizeRecommendationItem` now trusts the model's date the same way `SCHEDULE_UPDATE` always has (see below), and `AiService.SYSTEM_PROMPT` explicitly tells the model not to substitute today's date. Drops any element with a blank/missing title (defensive — a model slip producing an empty item shouldn't surface as a blank card), and caps the list at `MAX_SCHEDULE_ITEMS_PER_RECOMMENDATION` (10, front-truncated with a warning log) to bound token cost and UI clutter. Each surviving element is persisted as its own `AiChatSuggestedSchedule` row (table `ai_chat_suggested_schedules`, FK to `AiChatMessage`, ordered by `itemOrder`) rather than reusing `AiChatMessage`'s old single `suggested*` columns — saved individually (not left to cascade) so the returned `AiChatMessageDto` has each item's real id immediately, needed for the per-item register endpoint below. `AiChatMessage.suggestedSchedules` is `CascadeType.ALL`+`orphanRemoval` so deleting/clearing a conversation (`deleteByUserId`, a derived — not `@Modifying`/bulk — delete method, so JPA cascades per-entity) cleans up its items too, no manual cleanup needed. The old singular `suggested*` columns on `AiChatMessage` are kept only for backward compat with pre-migration rows (`registeredScheduleId` likewise) — new `SCHEDULE_RECOMMENDATION` rows always leave them null and populate `suggestedSchedules` instead; `AiChatMessageDto.suggestedItems` is the new list, and `dashboard.js`'s `aiChatAssistantBubbleHtml` renders per-item cards (`aiChatSuggestionItemHtml`) when `suggestedItems` is non-empty, falling back to the legacy single-field rendering only when it's empty but `suggestedTitle` is present (i.e. an old row). Each item gets its own manual/auto-register actions (`PATCH /api/ai/chat/messages/{id}/items/{itemId}/register` → `AiService.markItemRegistered`, ownership checked against the parent message since an item doesn't carry a user itself) so registering one doesn't require acting on the rest in the same turn; a "전체 자동 등록" bulk button appears when there's more than one still-unregistered eligible item and the auto-register setting is on. `maybeAutoRegisterAfterSend` (the no-click auto-register path) loops the same per-item eligibility (`canAutoRegisterItem`: title/startAt/categoryId all present) over the whole list when `suggestedItems` is non-empty, continuing past individual save failures rather than aborting the batch. Because a full 10-item response (each with a verbose `content`, e.g. a workout plan with sets/reps) can be large, `AiConfig.chatModel`'s `max_tokens` was bumped from the Spring AI default (500 — fine for the old single-suggestion shape) to `CHAT_MAX_TOKENS = 4096`, same value and same reasoning as `mandalartFillChatModel`'s bump below — otherwise the JSON response truncates mid-string and `BeanOutputConverter` throws a parse error instead of a usable `AiScheduleSuggestion`.

**AI-driven schedule updates** (`SCHEDULE_UPDATE`): `AiService` shows the model each in-context schedule's id (`[id:N][STATUS] title (...)`, see `buildScheduleContext`/`getWindowedSchedules`) so it can reference one via `AiScheduleSuggestion.targetScheduleId`. That id is only trusted if it's actually in the same windowed id set shown this turn (`windowedScheduleIds.contains(...)`, defense against a fabricated/stale id) — otherwise it's nulled and the frontend won't offer either action button at all. Update suggestions do **not** get their date forced to today (a reschedule like "내일로 옮겨줘" needs to land on a different day) — `SCHEDULE_RECOMMENDATION` now behaves the same way (see above). The model is instructed to echo back unchanged fields from the target's current values (partial-intent → full-object translation), since `PUT /api/schedules/{id}` requires a full `ScheduleRequestDto`, not a patch.

Frontend gives two actions on a `SCHEDULE_UPDATE` bubble (mirrors the 수동/자동 pattern on `SCHEDULE_RECOMMENDATION` bubbles): "수정" opens the *existing* edit modal for `targetScheduleId` via `openEditModalFromAiSuggestion` (pre-filled with the schedule's real current values, including `status`, which the AI never touches; only the fields the suggestion actually set get overwritten) for review before saving through the normal `PUT` flow — no immediate write. "수정 반영" calls `applyAiUpdateToSchedule` → `saveAiUpdateAsSchedule`, which `PUT`s immediately with no modal: it starts from the target schedule's *current* values (`status` always preserved, since AI never sets it) and layers the suggestion's fields on top, falling back to the current value for `title`/`categoryId`/`startAt` if the suggestion left them null (i.e. `AiService`'s own validation rejected what the model sent) — except `endAt`, which is trusted as-is even when null, since null there is a legitimate "convert to reminder-type" outcome, not just a validation failure. `registeredScheduleId`/`markRegistered` is reused as the generic "this suggestion resulted in schedule X" link for both create and update (badge text branches on category) regardless of which of the two actions was used.

**AI auto-register without confirmation**: when `User.aiAutoRegisterEnabled` is on, `dashboard.js`'s `maybeAutoRegisterAfterSend` fires right after a `SCHEDULE_RECOMMENDATION` exchange resolves (only if `canAutoRegister` — title/startAt/categoryId all present) and saves it immediately via `saveAiRecommendationAsSchedule`, no button click required. It does *not* close the chat panel or jump to the schedule detail view (unlike the explicit "자동 등록" button path, `autoRegisterAiChatMessage`, which still does both since that's a deliberate user action) — it just re-renders the bubble to show the "✅ 등록됨" badge and toasts. The button itself is left in place as a manual fallback (network failure, or reviewing older un-acted-on history after reopening the panel — that history is *not* retroactively auto-registered, only the freshly-received exchange is).

**AI rate limiting**: `AiService.sendMessage` calls `AiRateLimiter.checkLimit(userId, userType)` before touching `ChatClient`. `ADMIN` is exempt; `USER` is capped at `AiRateLimiter.LIMIT_PER_MINUTE` (5) calls/minute via a Redis fixed-window counter (`ai-rate-limit:{userId}`, `INCR` + `EXPIRE` set only on the first increment of each window) — same idiom as `AuthService`'s refresh-token bookkeeping, using the autoconfigured `StringRedisTemplate` (`RedisTemplate<String, String>`) rather than the JSON-serializing `RedisTemplate<String, Object>` bean from `RedisConfig`. Fails open on Redis errors (same pattern as `JwtAuthenticationFilter`'s blacklist check / `ScheduleService`'s cache eviction) — a Redis outage degrades to "no rate limiting" rather than blocking the AI chatbot. Exceeding the limit throws `BusinessException(ErrorCode.AI_RATE_LIMIT_EXCEEDED)` → 429.

**Recurring schedules**: `domain/recurringschedule` stores a weekly recurrence rule (`startTime`/`endTime` + `daysOfWeek` as a `"MONDAY,WEDNESDAY,..."` CSV column — no join table) and expands it into individual `Schedule` rows via `RecurringScheduleService`.

**Automation settings**: `User.autoStatusMode` (toggle via `PUT /api/users/me/auto-status-mode`) — purely a frontend-facing flag read by the dashboard to decide whether to show manual status-change controls; the actual automatic `PENDING → IN_PROGRESS → COMPLETED` transitions run regardless based on schedule start/end times.

**Mandalart**: `domain/mandalart` is a 9x9-grid CRUD feature (board + cells, `MandalartService`) with ownership checks, plus AI-assisted fill (`MandalartAiService`, `POST /api/mandalart/{boardId}/ai-fill`). Classic Mandalart layout: cell `(4,4)` is the main goal; the 8 cells surrounding it in the center block (`(3,3)`, `(3,4)`, `(3,5)`, `(4,3)`, `(4,5)`, `(5,3)`, `(5,4)`, `(5,5)`) are the sub-goals; each of the 8 *outer* 3x3 blocks has its own center cell (e.g. `(1,1)` for the top-left block) that's supposed to be a copy of the matching sub-goal, surrounded by 8 action-item cells. `fillWithAi`: (1) mirrors each sub-goal into its outer block's center cell purely in code (no AI call, since it's an exact copy) via `mirrorSubGoalsToOuterBlockCenters`, then (2) sends only the still-empty cells (usually the 64 action items) to a **separate** `ChatClient`/`ChatModel` bean pair (`mandalartFillChatClient`/`mandalartFillChatModel` in `AiConfig`, `max_tokens=4096` vs the default chat bean's much smaller budget — a 64-cell JSON response needs the extra headroom or it truncates) requesting a `MandalartFillSuggestion` (list of `{row, col, content}`). Suggested cells are only applied if their coordinate was actually in the empty-set requested this turn (defensive validation, same pattern as `targetScheduleId`/`targetMandalartBoardId`) — **already-filled cells are never touched**, which is what makes it safe to auto-apply without a review step. Also rate-limited via `AiRateLimiter` (same 5/min budget as chat).

Note on Lombok + `@Qualifier`: `@RequiredArgsConstructor` does **not** copy a field's `@Qualifier` onto the generated constructor parameter (verified by decompiling — confirm with `javap -v` before trusting it, not from memory) unless `lombok.config` explicitly allowlists it, which this repo doesn't have. `MandalartAiService` instead relies on the field being *named* `mandalartFillChatClient` to match that `@Bean`'s name via Spring's by-name disambiguation fallback — don't rename that field to something generic like `chatClient` without re-verifying the correct bean gets wired (it would silently wire the *other* `chatClient` bean instead, by name).

**Mandalart RAG (past-goal retrieval for `fillWithAi` few-shot)**: `MandalartGoalEmbeddingService` embeds completed outer blocks (sub-goal text + its 8 filled action items, joined) as pgvector documents via Spring AI's `VectorStore`/`PgVectorStore` (auto-configured — see `spring.ai.vectorstore.pgvector.*` in `application.yml`, table/HNSW index self-initializes via `initialize-schema: true`, independent of Hibernate's `ddl-auto: validate`). Anthropic doesn't offer an embedding model, so embeddings are OpenAI `text-embedding-3-small` (`spring.ai.openai.embedding.options.model`) — the OpenAI starter also auto-configures an unused `OpenAiChatModel` bean by default, disabled via `spring.ai.openai.chat.enabled: false` since only its embedding model is wanted. Local setup needs the `vector` and `uuid-ossp` Postgres extensions (`PgVectorStore`'s default id column uses `uuid_generate_v4()`) — `brew install pgvector` + `CREATE EXTENSION IF NOT EXISTS vector;` + `CREATE EXTENSION IF NOT EXISTS "uuid-ossp";` against the local `api` DB, plus an OpenAI API key in `application-local.yml`. Because the vector store's `id` column is `uuid`, not an arbitrary string, document ids are `UUID.nameUUIDFromBytes("board:{boardId}:block:{blockRow}:{blockCol}")` — deterministic per (board, block) so re-indexing the same block upserts (`PgVectorStore.add` is `ON CONFLICT (id) DO UPDATE`) instead of duplicating. Indexing is triggered from both write paths that can complete a block: `MandalartService.updateCell` (via `resolveAffectedBlock`, which maps an edited cell to its outer block — sub-goal cells map to their paired outer block, action-item cells to their own block, the main goal `(4,4)` isn't indexable) and `MandalartAiService.fillWithAi` (all 8 outer blocks re-checked after `applySuggestion`, since AI fill can complete several at once; already-complete blocks just upsert the same content, a cheap no-op in practice). `MandalartService.deleteBoard` deletes the board's embeddings too (deterministic ids for all 8 blocks, no read-before-delete needed).

At fill time, `MandalartAiService.buildFewShotContext` searches, per currently-filled sub-goal, for the single most similar past block scoped to the requester's own boards only (`userId` filter) and excluding the board being filled (`boardId != this board`) — manalart boards have no `Category`-style sharing, so cross-user leakage would be a real privacy issue, not just noise. Up to 3 matches total get appended to the fill prompt as `[참고: 과거 비슷한 목표의 실행항목 예시]`; zero matches (new user, no completed blocks yet) means the section is omitted entirely rather than a "no examples" filler line, keeping the terse prompt style. Indexing, search, and the board-delete cleanup are all fail-open (try/catch + `log.warn`, same pattern as `CacheFailSafeErrorHandler`/`JwtAuthenticationFilter`'s blacklist check/`AiRateLimiter`) — an OpenAI or pgvector outage degrades to "no few-shot examples this time," it never blocks saving a cell or running `fillWithAi` itself.

**Schedule RAG (semantic recall beyond the fixed ±2-week window)**: `ScheduleEmbeddingService` embeds every user-created/updated `Schedule` (`title` + `content`, falling back to `title` alone when `content` is blank) as a pgvector document — same `VectorStore`/`PgVectorStore` infra as the mandalart RAG above, since a second embedding-model bean wasn't worth standing up. `AiService.sendMessage` still builds its primary `[기존 일정]` context from the fixed ±2-week window (`filterToWindow`, unchanged) — RAG doesn't replace that (a literal "what's tomorrow" question needs the actual windowed list, not a semantic match on the phrase "tomorrow"), it only adds a `[참고: 의미상 비슷한 과거/예정 일정]` section for schedules *outside* the window that are semantically similar to the current message (`ScheduleEmbeddingService.findSimilarScheduleIds`, capped at `RAG_SCHEDULE_TOP_K = 5`, `docType`+`userId` filtered, excluding ids already in the windowed set). Because `AiService` already fetches the requester's **entire** schedule history every turn (`scheduleService.getSchedules(..., null)`, unbounded — `filterToWindow` just filters that in memory), the RAG step only needs matched schedule ids back from `VectorStore.similaritySearch`; display text is re-rendered from the already-fetched live `ScheduleResponseDto`s via the same `buildScheduleContext` formatter used for the windowed list, so there's no second DB round-trip and no risk of showing stale metadata. RAG-matched ids are unioned into the same "shown this turn" trusted-id set used for `SCHEDULE_UPDATE`'s `targetScheduleId` validation — so "그 저번 분기 킥오프 다음 주로 옮겨줘" can now target a schedule from months ago, not just one from the last two weeks. Indexing hooks into `ScheduleService.createSchedule`/`updateSchedule`/`deleteSchedule` only (mirrors `MandalartService.updateCell`/`deleteBoard`) — deliberately **not** `createSchedules` (the batch path `RecurringScheduleService` uses to expand a recurring rule into many occurrences at once) or `autoTransitionScheduleStatuses` (status-only changes, title/content untouched): batch-indexing dozens of recurring rows synchronously in one request would be a real latency hit with no async/queue infra in this codebase to soften it, and recurring occurrences are repetitive boilerplate anyway, low-value for "recall a specific past event." Same fail-open contract as the mandalart side.

Both RAG use cases share the *same* `vector_store` table (one `VectorStore` bean, no per-domain table split), so every document's metadata carries a `docType` (`"mandalart_block"` vs `"schedule"`) and every filter expression constrains on it — without that, a `userId` value colliding across domains would let one domain's search return the other's documents.

**AI-assisted mandalart via chatbot**: `AiResponseCategory.MANDALART_FILL` is a 4th classification alongside the schedule ones. Unlike `SCHEDULE_RECOMMENDATION`/`SCHEDULE_UPDATE` (which stage a suggestion for the frontend to apply), `AiService.sendMessage` calls `MandalartAiService.fillWithAi` **directly, synchronously, in the same request** the moment it validates `targetMandalartBoardId` against the user's own boards (context built by `AiService.buildMandalartContext`, showing each board's id + title + main-goal text so the model can disambiguate boards with similar titles) — no separate "apply" step exists in the frontend, because the underlying fill is already safe (empty-cells-only). This means a single chat turn classified as `MANDALART_FILL` can make **two** real Anthropic calls (classification + the fill itself) and burns through `AiRateLimiter`'s budget twice — accepted tradeoff, not a bug.

Note: TASKS.md describes the original task plan (session-based auth, `domain/schedule` field names like `repeatType`) and is intentionally left as a historical design record — the actual implementation diverged (JWT-based auth instead of session, `Schedule` uses `content`/`status` instead of `description`/`repeatType`). README.md, by contrast, is kept in sync with the current implementation — trust it (and the code) over TASKS.md.

## Testing

- When adding new logic (new service methods, new endpoints, new business rules), write accompanying test code in the same change — don't leave it for a follow-up ask.
- Match existing conventions: JUnit 5 + Mockito (`@ExtendWith(MockitoExtension.class)`, `@Mock`/`@InjectMocks`), AssertJ assertions (`assertThat`, `assertThatThrownBy`), Korean `@DisplayName` describing the scenario (see `UserServiceTest`, `AuthServiceTest`). Cover both success and failure/exception paths.
- Before reporting a change as done, actually run it: at minimum `./gradlew test --tests "<AffectedClass>"` for the touched class(es), or the full `./gradlew test` when the change spans multiple classes/layers. Don't claim success from reading the code alone — if tests can't be run (e.g. missing local MySQL/Redis), say so explicitly instead of asserting it works.
- `ScheduleServiceTest.apiPerformance` is tagged `@Tag("performance")` and requires the local DB to already have the seed categories the README's DB setup section describes — it's a manual benchmark, not a CI gate. `./gradlew test` (no flags, normal local/agent workflow) still runs it; only `./gradlew test -PciBuild` (what the GitHub Actions `test` job uses, see `DEPLOYMENT.md`) excludes it, since the CI pipeline's ephemeral service-container DB starts empty every run.

## Git workflow

- Commit freely per unit of work; no need to ask before committing.
- As of commit `d933707` ([CHORE-2] CLAUDE.md 추가 (#10)), commit messages follow: `[<category>-<n>] <설명> (#<m>)`.
  - `<category>` = commit type (`feat`, `chore`, `test`, ...), same types as the old `feat:`/`chore:` prefixes.
  - **Lowercase** (e.g. `[test-2]`, not `[TEST-2]`). Already-pushed commits `d933707`/`5db74ed` used uppercase (`[CHORE-2]`, `[CHORE-3]`) before this was corrected and were left as-is since rewriting published history isn't safe; unpushed commits were rewritten to lowercase before push.
  - `<n>` = 1-indexed count of prior commits in that category, computed from `git log --oneline`. Before this scheme, history used bare `feat:`/`chore:` prefixes (6 `feat`, 1 `chore`, 2 with no prefix, excluded from counts) — that history counts toward `<n>`.
  - `<m>` = 1-indexed count of *all* prior commits total (`git log --oneline | wc -l`), since this repo pushes directly to `main` with no PR flow and has no real PR/issue numbers to reuse.
  - Recompute both counts from current `git log` before each commit — don't reuse cached numbers from a prior session.
- Older commits (pre-`d933707`) used `<type>: <description>` (e.g. `feat: add ...`, `chore: ...`) — superseded by the scheme above, kept here only for history context.
- Always ask for explicit confirmation before `git push` (this repo pushes directly to `main`, no PR flow) — never push proactively.
- Never amend or force-push without the user explicitly asking.
